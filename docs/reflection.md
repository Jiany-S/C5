# Reflection

I placed the read-only boundary around published service information, the Action boundary around one committed expression of interest, and the Orchestration boundary around verification followed by conditional recording. Exactly three tools fit this narrow use case because each category has a visible purpose that can be demonstrated independently. The Action tool still checks service membership so direct callers cannot bypass the store's domain rules, while the Orchestration tool returns the verified service and actual sequence. This creates some intentional overlap: live model runs sometimes chose orchestration for a repeated recording request. That remained safe because both interfaces share the same atomic duplicate rule, but it showed why Chapter 5 emphasizes similarity between tools as well as their number. A larger business would need separate scheduling and communication capabilities; this toolkit makes no claim to provide either.

Implementation exposed practical issues beyond choosing decorators. The current FastMCP release required an update-check setting of `off`, rather than a Boolean-like string, so startup was checked against the installed API instead of copied blindly from older examples. Tests also caught a helper argument collision, and a separate Windows demo revealed that SQLite's transaction context manager does not close connections. Explicit connection closure and a database-release regression test resolved the latter. Live OpenAI tests showed that correct tool execution does not automatically ensure precise prose: an early response overstated the staff response target, and another omitted the duplicate record ID. Instructions and an explicit repeat prompt improved those answers, while saved initial reports preserve the observed shortcomings. Future work would use a structured final-answer contract, authenticated consent evidence, retention controls and a lifecycle for updating or closing interests. For this assignment, local deterministic facts, bounded interfaces and transactional persistence keep the implementation understandable and testable.
